01 — Executive Summary

State of the Component Layer & Target Architecture

Current state (verified in codebase)

The React web app is a genuine no-build runtime: js/core/react-runtime.js re-exports window.React/window.ReactDOM and aliases React.createElement to h. There is no JSX, no bundler, no npm build step — every view is an ES module imported directly by the browser and composed with h(tag, props, ...children) calls. js/views/screen-registry.js wires 70 screens into ScreenRegistry, and js/components/ui/ already holds a first-generation kit: AppShell, Sidebar, Topbar, DataTable, StatsCard, StatusPill, Drawer, Modal, LoadingSkeleton, EmptyState, PageHeader, SearchBar, ActionBar, FilterPanel, Badge, FormSection, plus domain cards (PartCard, SellerCard, VehicleCard). Styling is one 17,400-line styles.css (plus a 392-line css/cockpit.css overlay already carrying the rejected "Cockpit/Aurora" navy-teal look with ck-* class names visible directly in dashboard-view.js and Sidebar.js/Topbar.js/AppShell.js). Client data today is fragmented: contacts-view.js renders two flat "Customers / Suppliers" balance lists, customer-aging-view.js is a standalone aging-bucket table with a "Send Reminder" action, and invoices/quotes/part-requests/loyalty each show customer context independently with no unified 360° view and no shared client-selection state.

Target architecture

Ignition introduces a four-layer CSS cascade (tokens → primitives → components → views) that coexists with the legacy stylesheet during migration, a second-generation component set under a new js/components/ignition/ namespace that composes over — never replaces in place — the existing UI kit, and two flagship screens: a rebuilt dashboard-view.js and a new client-workspace-view.js that unifies contacts, aging, invoices, payments, quotes, part requests, vehicles, loyalty, and communications into one customer-360 shell. Both consume the same ApiClient (js/core/api-client.js, unchanged) and the same ScreenRegistry wiring pattern already used by all 70 screens, so shipping Ignition on 2 screens is additive and reversible — the other 68 screens keep rendering exactly as they do today, untouched, on styles.css.

Non-negotiable constraints this architecture honors

  • No JSX, no bundler, no transpile — every new file is a plain ES module using h(), importable by <script type="module"> directly from wwwroot.
  • One type/component per file — every Ignition primitive and composite gets its own file, named after the export, mirroring the existing js/components/ui/*.js convention.
  • Zero regressions on the 68 untouched screens — token layer is additive CSS custom properties scoped under an opt-in root class, not a global reset.
  • Existing ApiClient contract (api.get/list/post/put/delete/postForm, ApiError shape) is the only data-access surface — no new fetch layer.

02 — Design-Token Architecture

Replacing 17,400 Lines with a Layered System

The token architecture is four physical files loaded in strict cascade order, added as new <link> tags after styles.css in index.html so Ignition rules win on selectors of equal specificity without deleting or rewriting the legacy file yet. Ignition surfaces are opt-in via a single root class, .ignition-root, applied only to the two new views' outermost container — the 68 legacy screens never receive this class and never see a token change.

Focus management

  • Opening CommandPalette/Drawer moves focus to the first focusable element inside (search input / first form field); closing returns focus to the trigger element (stored via useRef before open, matching the ref pattern already used across existing views).
  • Focus trap inside open overlays: Tab/Shift+Tab cycle within the overlay only — implemented with a small focusable-elements query helper, no new dependency.
  • Route change (IconRail select / ClientRail select) sets focus to the new region's h1/heading via a shared useFocusOnChange(dep) hook so screen readers announce navigation.
  • :focus-visible only (not :focus) shows the 2px orange ring, so mouse clicks stay visually clean while keyboard nav stays fully legible.

Optimistic UI — payment & invoice actions

// pattern: apply locally, reconcile with server response, roll back on ApiError
async function recordPayment(invoiceId, amount) {
  // 1. optimistic patch — DataGrid row updates instantly
  setInvoices(prev => prev.map(inv =>
    inv.id === invoiceId
      ? { ...inv, paidAmount: inv.paidAmount + amount, status: "Pending sync" }
      : inv));

  try {
    const updated = await api.post(`/api/sales/${invoiceId}/payments`, { amount });
    // 2. reconcile with server truth
    setInvoices(prev => prev.map(inv => inv.id === invoiceId ? updated : inv));
    toast.success("Payment recorded.");
  } catch (error) {
    // 3. rollback + surface ApiError.message (existing ApiClient contract)
    setInvoices(prev => prev.map(inv => inv.id === invoiceId ? originalRow : inv));
    toast.error(error.message || "Payment failed — reverted.");
  }
}

Applies to: payment recording, quote status change, part-request status change, reminder send (button shows inline spinner but list item itself does not optimistically change, since delivery is asynchronous and best confirmed by the existing reminderCustomerId-style pending-state pattern already in customer-aging-view.js).

Skeleton loading choreography

  1. T+0ms: view mounts, all regions render LoadingSkeleton variants matching final layout shape (existing component, reused as-is — variant="stats" for KpiBand, variant="rows" for DataGrid/ClientRail, variant="cards" for InsightPanel).
  2. T+≤150ms: if data resolves before this threshold, skip the skeleton fade-in entirely to avoid flash-of-loading-state on fast connections.
  3. Data arrives: skeleton cross-fades to real content over 160ms (--ig-dur), region by region as each Promise.all branch resolves — KpiBand and ClientRail can populate before TrendChart/ActivityTimeline finish.
  4. Virtualized DataGrid threshold: rows > 150 auto-enables windowing (fixed 44px row height, ~12 rows rendered + overscan 4); below 150 rows renders fully, matching current DataTable behavior with zero risk of regression for the majority of screens (aging table today typically renders 20-60 rows).

Module loading strategy (no-build runtime)

  • Every Ignition component file is a native ES module (export function X(){}), loaded by the browser's module graph via static import — no bundler means no code-splitting tooling, so the strategy is discipline in the import graph, not a build config: shell components (IconRail, CommandBar) import eagerly since every screen needs them; heavy, screen-specific pieces (TrendChart, ActivityTimeline) are only imported by the views that render them, so browser HTTP/2 module fetching naturally lazy-loads per-route.
  • <link rel="modulepreload"> added to index.html for the shell components (AppShell/IconRail/CommandBar/tokens) so they're warm before the router resolves the first screen — same technique already usable with zero new infra since these are static files served by the existing ASP.NET static-file host.
  • All 4 CSS layer files are small (tokens ~2KB, primitives ~4KB, components ~14KB, per-view ~3KB) — total new CSS payload for the two Ignition screens stays under 25KB gzipped, versus continuing to grow the single 17,400-line file.

Memoization rules

  • Derived view-model computations (aging totals, KPI deltas, category rollups) wrapped in useMemo keyed on the raw API arrays — ports the existing pattern already present in customer-aging-view.js (totals, over30, over90 via useMemo) rather than introducing a new pattern.
  • List item renderers (ClientRail rows, DataGrid rows) are plain functions, not wrapped in React.memo, unless profiling on the real dataset shows re-render cost — the runtime exposes useMemo/useCallback only (see react-runtime.js), no memo/lazy re-export today; adding that export is a one-line, low-risk addition to react-runtime.js if profiling later requires it.
  • Event handlers passed to list rows are created once per row via a stable factory keyed by id (onSelect(row.id) curried at row-render time is acceptable at current data volumes — client lists are typically <500 rows per tenant).

Chart rendering approach

All charts (TrendChart, KpiTile sparkline, AgingBar) are hand-built inline SVG using the same technique already proven in dashboard-view.js's ckLinePath()/ckSpark() helpers — no charting library dependency, no new bundle weight, full styling control via CSS custom properties (stroke/fill reference --ig-orange etc. so dark/light theme switching repaints charts for free without JS re-computation).
