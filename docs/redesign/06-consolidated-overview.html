Section 01
Executive Summary
A from-scratch redesign of the two screens where the business actually lives — grounded in the current codebase, quantified, and ready to build.

What this package is. "Ignition" is a complete, ground-up redesign of the SpareParts Dashboard and a new unified Client Workspace, produced by a six-agent design team as six companion reports. It replaces the rejected "Aurora" navy/teal direction with a deliberately unmistakable identity — carbon black surfaces (#0a0a0b / #131316 / #1b1b1f), a single electric-orange accent (#f97316), Plus Jakarta Sans / Inter / JetBrains Mono type, borderless shadow cards at 16px radius, a 72px icon rail, and a global Ctrl+K command bar. Every claim in the package is grounded in real files: screen-registry.js (70 registered screens), dashboard-view.js (663 lines, 7 API calls on mount), the 17,400-line styles.css, and the existing OwnerCockpitService aggregate.

The two screens. (1) The Dashboard becomes a command center: a KPI band of tabular-numeral tiles, a 7-day trend, and — promoted to the organizing principle of the screen — the Action Queue, which scores exceptions by severity × money at stake, carries a lifecycle (appears → acted → resolved/dismissed), and deep-links to the exact entity, not just a screen. (2) The Client Workspace replaces six fragmented screens (Contacts, Customer Aging, Invoices, Quotes, Part Requests, WhatsApp) with one customer-360 record — identity, balance and aging buckets, invoices, payments, quotes, requests and communications as tabs of a single view, where a payment can be received and a reminder previewed and sent without navigating away.

How it ships. Everything is additive. The backend adds 8 new endpoints and changes none (/api/owner-cockpit and friends keep working for WPF and mobile until each migrates on its own schedule). The web app adds a four-layer token CSS cascade after styles.css and two rebuilt views; the other 68 screens render exactly as today. Rollout is side-by-side for four weeks with telemetry gates — legacy screens retire only when measured targets are hit (counter sale p50 ≤35s, queue dismissals ≤15%), never on a calendar date, and file deletions require Ralph's explicit approval per the workspace safety rules.

Bottom line for the dev team: two screens, ~24 new frontend files, 8 additive endpoints, 4 covering indexes, one token contract shared by web, WPF and mobile — with a measured payback of roughly one working month of staff time per shop per year if the projections hold, and instrumentation to prove whether they do.

Most important decisions

2.1
Carbon + one orange accent. Three-step surface elevation #0a0a0b → #131316 → #1b1b1f (+ #232328 pressed), accent #f97316 (hover #ea580c) used sparingly enough that orange always means "look here", four semantic status colors (#22c55e / #fbbf24 / #ef4444 / #38bdf8). Full 50–900 ramps for neutral and orange; complete light-mode inversion included.
2.2
Three-typeface stack with strict roles. Plus Jakarta Sans (display, −0.04em tracking), Inter (body — disappears at small sizes in dense tables), JetBrains Mono reserved exclusively for tabular numerals: prices, quantities, aging buckets.
2.3
Borderless shadow cards, 16px radius, dark-first. Cards separate by layered shadow and one-shade surface shifts, never borders; geometry gets sharp only for status (pills, 2px orange active-nav rail).
2.4
Single stroke icon family. 24×24 grid (20×20 live area), 1.75px stroke, round caps/joins, stroke-only with accent fill reserved for active state; optical sizes 14/16/20/28px.
2.5
One token system, three implementations. The §13 table is the cross-platform contract: CSS --ig-* custom properties ↔ WPF IgnitionTheme.xaml ResourceDictionary keys (IgBrushAccent…) ↔ React Native theme.js. 72px rail on desktop/web; bottom tabs + 44px targets are mobile's only sanctioned deviations.
Workflow gate: per the Design Change Workflow in CLAUDE.md, the hero mockups in this report (pages 8–12) are the "before pictures" Ralph must approve before any implementation phase starts, and post-implementation screenshots must be compared back to them.

3.1
Four-layer CSS cascade, additive to the legacy file. tokens.css → primitives.css → components.css → views.*.css linked after the 17,400-line styles.css; every rule scoped under an opt-in .ignition-root class so the 68 untouched screens can't regress. Total new CSS <25KB gzipped.

Explicit do-not-touch list (styles.css, api-client.js, all 66 other views); superseded views stay on disk pending Ralph's deletion approval.

System Architecture — Read Models & Contracts
docs/redesign/04-system-architecture.html · 13 pages
Author
dev-backend-api — Backend API Agent
Purpose
The composed endpoints, JSON contracts, SQL, caching and security the two screens bind to
Posture
Everything additive — zero changes to any currently shipping endpoint; WPF/mobile unaffected

Section list

  1. Executive Summary (chatty-call inventory)
  2. Dashboard Read Model — GET /api/dashboard/summary
  3. Dashboard — Example Payload
  4. Caching & Invalidation
  5. Client Workspace Read Model — GET /api/clients/{id}/workspace
  6. Workspace Child Resources (paged tabs + typeahead)
  7. Data Layer — Aggregate SQL & Covering Indexes
  8. Performance Engineering (N+1, compression, ETag)
  9. Security Architecture
  10. Sequence Diagrams
  11. Versioning & Rollout

Most important decisions

4.1
One composed dashboard endpoint. GET /api/dashboard/summary wraps the existing OwnerCockpitService (unchanged) plus new DashboardActionQueueService and DashboardTrendService, collapsing 7 client calls to 1. Budget: ≤350ms p95 server time cold, ≤12ms on ETag 304; core P&L stays in one DbSession for consistency, independent reads parallelize via Task.WhenAll on separate short-lived connections.
4.2
The Client Workspace becomes a backend resource. GET /api/clients/{id}/workspace (header + balance + aging + KPIs, 20s TTL) with five independently paged child routes — /invoices /payments /quotes /part-requests /timeline — plus /api/clients/search typeahead. 8 new endpoints total.
4.3
Cache + ETag polling, not SignalR. Per-tenant cache keys (dash:tenant:{id}:{date}, 45s TTL) with explicit write-path invalidation on sales/payments so money is never stale; dashboard "Live updates" polls at 30–60s with If-None-Match. SignalR rejected for cost and cross-tenant-broadcast risk.
4.4
Covering indexes ship first. Additive migration (e.g. IX_Transactions_Tenant_Type_Date INCLUDE(...)) deployable ahead of code; every query keeps the codebase's tenant-guard shape (@TenantId = 0 OR t.TenantId = @TenantId) with TenantId sourced only from the JWT via ITenantContext — never from a request.
4.5
Security invariants. Class-level [Authorize] on both new controllers; uniform 404 for missing or cross-tenant customers (enumeration prevention); zero tenantId/dbName/cache-key leakage in wire DTOs; production-safe ProblemDetails errors; search rate-limiting partitioned by tenant, not IP.

Most important decisions

5.1
The headline numbers. Across the 10 highest-frequency tasks: 799 → 358 UI steps per shop-day (−55%), projected ~98 min/day recovered (~47 min counter staff, ~43 min owner, ~8 min quoting — ~1.6h, one working month/year); 2-line counter sale 95s → ~30s. Fig 6's whole-day model shows the UI tax falling 98 → 41 min (−58%). Assumed frequencies are replaced by measured counts during rollout.
5.2
Action Queue as a workflow engine, not a hint list. Items scored by severity × money at stake, full lifecycle (appears → acted → resolved/dismissed) that survives refresh, and a deep-link contract into the exact entity-level action — upgrading the existing buildActionQueue() six signals.
5.3
Ctrl+K grammar. Terse verbs: inv eli (invoice for Elie), pay eli 250, part n54 coil (inline stock/price card — no navigation), q eli, c eli, cust +, wa eli, #8811, > screen. <50ms keystroke-to-result on cached index; barcode scanners act as keyboard wedges into the same field.
5.4
Missing flow discovered and fixed: receiving a payment. Today it has no UI path at all (manual journal in Accounting); the Workspace payment sheet makes it a 3-step flow with oldest-first allocation (T4 target: 3min → ≤45s).
5.5
Metric-gated rollout, not calendar-gated. 4-week side-by-side (opt-in weeks 1–2, default weeks 3–4), 6 telemetry event families, 9 success metrics (e.g. T2 p50 ≤35s, queue same-day resolution ≥70%, dismissals ≤15%), and hard rollback criteria (T2 p50 >60s or dismissals >30% at week 4 flips the default back).
Count note for implementers: Report 05 counts 74 registry entries where Reports 01/03 count 70 — the registry grew during the package's production. Treat screen-registry.js at build time as the source of truth; the "68 untouched screens" guarantee means "all registered screens except the two Ignition rebuilds".
